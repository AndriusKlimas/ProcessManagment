Changes explained
=================

Current status
--------------

The MariaDB migration described in the historical sections below has been
reverted. The application currently uses Redis for catalog, login, and history
storage. KinD, Ingress, Samba, and the automated setup remain active.

Purpose
-------

This project was changed from a Redis-based, Minikube-oriented setup into a
KinD-based local Kubernetes setup that can use Samba storage and MariaDB.
The goal is to run the project on a laptop while keeping the setup repeatable.


1. KinD cluster
---------------

File: kind-config.yml

The KinD cluster is named music-app and contains:

- One control-plane node.
- Two worker nodes.
- Host port 80 mapped to port 80 in the control-plane node.
- Host port 443 mapped to port 443 in the control-plane node.
- An ingress-ready label on the control-plane node.

The ingress-ready label is used because the host ports are mapped only to the
control-plane node. The NGINX Ingress controller must be scheduled there for
http://localhost to work.

2. Ingress routing
-------------------

File: ingress-controller-patch.json

This patch adds a node selector to the NGINX Ingress controller so it runs on
the ingress-ready control-plane node.

File: base/dev/kustomization.yml

The development overlay now uses the music-app namespace. This is important
because the application services are in music-app and an Ingress can only route
to Services in its own namespace.

Without this namespace setting, the Ingress was created in default and looked
for services such as default/login-page-svc, which do not exist.

3. Samba storage
----------------

Directory: samba

The Samba server from the separate project was copied into this repository:

- samba/docker-compose-samba.yml starts the Samba container.
- samba/Dockerfile builds Ubuntu with Samba and creates user k8s.
- samba/smb.conf exposes the sambashare share.
- samba/startup.sh starts Samba in the foreground.
- samba/storage/html is the host directory mounted into the share.

The Kubernetes nodes access the share as:

    //samba/sambashare

The Samba username is k8s and the development password is password. Change
these values before using this outside local coursework.

File: base/deployment/samba-storage.yml

This creates:

- Secret smbcreds for the Samba credentials.
- StorageClass smb using the Samba CSI driver.
- PersistentVolumeClaim song-storage.

The StorageClass uses ReadWriteMany so the share can be mounted by workloads
on different KinD nodes.

File: base/deployment/song-player-nginx-depl.yml

The song-player-nginx Deployment mounts song-storage at:

    /usr/share/nginx/html

File: base/deployment/song-player-nginx-svc.yml

The internal Service port was changed from 8081 to 80. This matches the Nginx
container and the AUDIO_BASE_URL value used by the application.

4. SMB CSI driver
-----------------

The setup installs the SMB CSI driver with kubectl manifests instead of Helm.
It installs the RBAC, driver, controller, and node plugin resources.

The driver is required before the song-storage PVC can mount the Samba share.
The driver is installed into kube-system and runs on the KinD nodes.

5. MariaDB operator
-------------------

Directory: maridb

The directory name is retained from the existing project, although MariaDB is
the correct spelling.

Files:

- maridb/mariadb-secret.yml contains the MariaDB root and application secrets.
- maridb/maria-db-cluster.yml contains the MariaDB operator custom resources.

The setup uses the MariaDB operator Helm charts:

- mariadb-operator-crds installs the MariaDB custom resource definitions.
- mariadb-operator installs the controller that reconciles those resources.

Helm must be available for this part. Smart App Control on Windows currently
blocks the installed helm.exe on this machine. The setup script stops early
until Helm is allowed or run from WSL.

6. MariaDB cluster design
-------------------------

The old maria-db-cluster.yml was an address-book example. It created an
address_book database, addr_svc user, and unrelated addr-svc Deployment.
Those resources were replaced.

The new MariaDB setup:

- Runs one MariaDB replica to reduce laptop memory usage.
- Uses the smb StorageClass for persistent storage.
- Runs in the music-app namespace.
- Creates catalog, login, and history databases.
- Creates separate users and grants for those databases.
- Creates a MaxScale service named mariadb-max on port 3306.

The application services connect to mariadb-max rather than directly to a
MariaDB pod.

7. Redis to MariaDB migration
------------------------------

The original catalog, login, and history services used Redis. They now use
PyMySQL and MariaDB.

Catalog service

File: catalog-svc/catalog-app.py

The catalog service now:

- Creates a products table if it does not exist.
- Seeds the original sample catalog when the table is empty.
- Reads catalog products with SQL SELECT queries.
- Inserts or updates products with SQL INSERT ... ON DUPLICATE KEY UPDATE.

Login service

File: login-page-svc/login-page.py

The login service now:

- Creates a users table if it does not exist.
- Stores SHA-256 password hashes in MariaDB.
- Checks users with SQL SELECT queries.
- Creates users with SQL INSERT queries.

History service

File: history-svc/history-page.py

The history service now:

- Creates a plays table if it does not exist.
- Stores username, song name, and timestamp for each play.
- Reads the latest 100 plays for a user.
- Deletes older plays so each user retains at most 100 entries.

All three services retry the MariaDB connection during startup while the
operator and database are still becoming ready.

8. Python dependencies
----------------------

The catalog, login, and history requirements files now use:

    PyMySQL==1.1.1

The Redis dependency was removed from those services because their data is now
stored in MariaDB.

9. Kubernetes application configuration
---------------------------------------

The application ConfigMap now contains:

    MARIADB_HOST: mariadb-max
    MARIADB_PORT: 3306

Each service Deployment receives its own database name, username, and password
from ConfigMap and Secret references.

The Redis database Deployments and Services were removed from the active
Kustomize overlay. Their old YAML files remain in base/deployment as historical
files but are no longer deployed by the overlay.

10. Automated setup
-------------------

File: setup-kind.ps1

The script performs the setup in this order:

1. Check Docker, kind, kubectl, and Helm.
2. Create the music-app KinD cluster if it does not already exist.
3. Start the repository-local Samba container.
4. Install the SMB CSI driver.
5. Install the MariaDB operator CRDs and operator with Helm.
6. Install the NGINX Ingress controller.
7. Pin the Ingress controller to the port-mapped control-plane node.
8. Create the music-app namespace.
9. Apply the MariaDB Secrets and custom resources.
10. Build and load the six application images into KinD.
11. Apply the base/dev Kubernetes overlay.

Run the first setup with:

    .\setup-kind.ps1

After rebuilding the images once, later cluster recreations can skip Docker
builds:

    .\setup-kind.ps1 -SkipImageBuild

The images still need to be loaded into a newly created KinD cluster.

11. Manual setup guide
----------------------

File: KIND-SETUP.txt

The manual guide contains the same steps as the script, including:

- KinD creation.
- Local Samba startup.
- SMB CSI installation.
- MariaDB operator installation.
- NGINX Ingress installation and scheduling patch.
- MariaDB resource application.
- Image build and loading.
- Application deployment and checks.
- Cluster cleanup.

12. Validation completed
------------------------

The following checks passed:

- Python syntax compilation for catalog, login, and history services.
- PowerShell parser validation for setup-kind.ps1.
- Kustomize rendering for base/dev.
- YAML diagnostics for the MariaDB resources and setup files.

A live MariaDB integration test has not been completed because the MariaDB
operator still depends on Helm, and Helm is currently blocked by Windows Smart
App Control. After Helm is available, verify with:

    kubectl get pods -n mariadb-operator
    kubectl get mariadb,databases,users,grants -n music-app
    kubectl get pvc -n music-app
    kubectl get pods -n music-app

Important development notes
---------------------------

- The passwords in the repository are development examples and should not be
  used for a real deployment.
- The one-replica MariaDB configuration is intentionally laptop-friendly; it
  does not provide database failover.
- The first image build after the MariaDB migration is required. Do not use
  -SkipImageBuild until the new images have been built successfully.
- If the KinD cluster is deleted, the Samba container can be recreated, but the
  images must be loaded into the new KinD nodes again.
